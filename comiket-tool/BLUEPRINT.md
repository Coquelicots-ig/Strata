# コミケ買い物分担ツール Blueprint（v0.1 草案）

## 1. 目的

数人のチームが Zoom 会議をしながら、コミックマーケットで「誰が何を誰の代わりに買うか」を決めて記録する。
参加者は全員が自分のスマホで操作し、最後に一覧を表示・出力する。

## 2. 要件の整理

| # | 要件 | 設計での扱い |
|---|------|--------------|
| R1 | 数人のチームで分担する | 1つの「部屋」に数人（想定 2〜10 人）が入る。メンバー名は会議の最初に登録する |
| R2 | Zoom で会議する | Zoom 自体には組み込まない。ツールは別の URL をブラウザで開く。進行役が一覧画面を画面共有できるようにする |
| R3 | 1つの購入物に依頼人は複数、請負人は1人 | `requesters` は配列、`assignee` は単一値（未定も可） |
| R4 | 参加者それぞれが操作して記録する | 共有データをリアルタイムで同期する。同時編集の衝突を防ぐ（7章） |
| R5 | Web カタログからダウンロードした DB を参照する | カタログ読込を「アダプタ」として分離し、形式が分かったら差し替える（5章） |
| R6 | DB は未入手なのでダミーデータで設計する | `dummy-data/catalog.csv` を同じ形で読む |
| R7 | ダミーデータの項目：何日目、サークル番号、サークル名、購入物、依頼人、請負人、備考 | `dummy-data/assignments.csv` に全項目の例を置いた |
| R8 | 何日目＋サークル番号で検索し、サークル名を表示、残りを入力する | 入力画面の流れ（6.2） |
| R9 | 最後に一覧表示と出力 | 一覧画面とエクスポート（6.3, 6.4） |
| R10 | 会議当日のみ公開する | 公開期間をサーバ側のルールで制限し、終了後に閉じる（8章） |
| R11 | スマホで操作する | スマホ縦画面を基準にした 1 カラムの画面。片手で押せる大きさのボタン |

## 3. 全体構成（推奨案）

```
[スマホのブラウザ] ──HTTPS──> [静的ホスティング: HTML/JS/CSS + カタログJSON]
        │
        └──リアルタイム同期──> [共有データストア（部屋ごとの購入物リスト）]
```

- **フロントエンド**：静的な 1 ページのアプリ（SPA）。アプリのインストールは不要。
- **カタログ**：読み取り専用。事前に JSON に変換して静的ファイルとして配る。端末側で検索するので、会議中にサーバへ検索を投げない。
- **共有データ**：購入物の記録だけを置く。複数の端末に変更がすぐ反映される必要がある。

### 共有データストアの候補

| 候補 | 良い点 | 気になる点 |
|------|--------|------------|
| A. Firebase（Firestore + Hosting）**推奨** | リアルタイム同期が標準。セキュリティルールで「当日の時間帯だけ書ける」を書ける。少人数なら無料枠に収まる見込み | Google アカウントと Firebase プロジェクトの準備が要る |
| B. Supabase | SQL で扱える。リアルタイム機能あり | 無料プロジェクトは一定期間使わないと停止する（当日のみの用途では問題になりにくい） |
| C. Google スプレッドシート + Apps Script | 出力がそのまま表になる | リアルタイム反映が弱く、同時編集の衝突処理を自作する必要がある |

料金・無料枠の数値は確認していないので、採用前に各サービスの最新の条件を確認する。

## 4. データモデル

### 4.1 カタログ（読み取り専用）

| 項目 | 型 | 例 | 備考 |
|------|----|----|------|
| `day` | 整数 | `1` | 何日目 |
| `circle_no` | 文字列 | `東A01a` | 正規化した形で持つ（4.3） |
| `circle_name` | 文字列 | `ダミーサークル壱` | |

キーは `(day, circle_no)`。日が違えば同じ番号でも別のサークルになる（ダミーデータに例あり）。

### 4.2 購入物（共有・編集可能）

| 項目 | 型 | 必須 | 説明 |
|------|----|------|------|
| `id` | 文字列 | ○ | 自動採番 |
| `day` | 整数 | ○ | 何日目 |
| `circle_no` | 文字列 | ○ | サークル番号（正規化済み） |
| `circle_name` | 文字列 | ○ | 検索時の値を写して保存する（カタログ差し替え後も記録が読めるように） |
| `item` | 文字列 | ○ | 購入物 |
| `requesters` | 文字列の配列 | ○（1人以上） | 依頼人。メンバー名から選ぶ |
| `assignee` | 文字列 / null | − | 請負人。1人だけ。未定なら null |
| `note` | 文字列 | − | 備考 |
| `created_by` | 文字列 | ○ | 最初に登録した人 |
| `updated_by` / `updated_at` | 文字列 / 時刻 | ○ | 最後に変更した人と時刻 |
| `version` | 整数 | ○ | 同時編集の検出用（7章） |

依頼人ごとの個数が必要かは未決（10章 Q3）。必要なら `requesters` を `[{name, qty}]` に変える。

### 4.3 サークル番号の正規化

スマホ入力では全角・半角、大文字・小文字、区切り記号がばらつくので、検索前にそろえる。

- 全角英数字 → 半角（`Ａ０１ａ` → `A01a`）
- ブロック記号の後の数字は 2 桁にそろえる（`東A1a` → `東A01a`）
- 末尾の `a` / `b` は小文字にそろえる
- 空白・`-` は取り除く

実際のカタログでの番号の書式（ホール名の表記、ブロック文字の種類）は未確認。DB 入手後にこの規則を見直す。

### 4.4 部屋とメンバー

| 項目 | 説明 |
|------|------|
| `room_id` | 推測されにくいランダムな文字列。URL に含めて配る |
| `members` | メンバー名の一覧。会議冒頭に進行役が登録する |
| `open_from` / `open_until` | 書き込みを許す時間帯（8章） |

## 5. カタログ DB の扱い

コミケ Web カタログからダウンロードできる DB の正確な形式（ファイル形式、列名、文字コード）は、こちらでは確認できていない。そのため次のように分ける。

1. **変換スクリプト**（事前に 1 回だけ実行）：入手した DB → `catalog.json`（4.1 の 3 項目だけ）
2. **アプリ**：`catalog.json` だけを読む

DB の形式が分かった時点で変換スクリプトだけを書けばよく、アプリ側は変えずに済む。
ダミーデータ段階では `dummy-data/catalog.csv` → `catalog.json` の変換で同じ流れを試す。

あわせて、カタログデータを会議用に再配布してよいかの利用条件も DB 入手時に確認する（10章 Q6）。
公開 URL に置く場合は、チーム外から取得されない形（部屋の URL を知る人だけ、当日のみ）にする。

## 6. 画面設計（スマホ縦画面）

画面は 4 つ。下部のタブで「入力」「一覧」「出力」を切り替える。

### 6.1 参加画面

- 部屋の URL を開くと表示される
- 「あなたは誰？」でメンバー名をタップして選ぶ（以後、端末に記憶）
- 進行役だけがメンバーを追加・変更できる

### 6.2 入力画面（中心の画面）

```
┌───────────────────────┐
│ [1日目] [2日目]          │ ← 大きなトグル
│ サークル番号 [東A01a   ] │
│ → ダミーサークル壱        │ ← 一致したら即表示
│───────────────────────│
│ このサークルの登録済み    │
│  ・新刊セット  依頼:A,B  │
│    請負:C   [編集]       │
│───────────────────────│
│ 購入物 [            ]   │
│ 依頼人 (複数選択)         │
│  [A✓][B ][C ][D ]       │
│ 請負人 (1人)              │
│  (A)(B)(C)(D)(未定)      │
│ 備考 [              ]   │
│        [ 登録 ]          │
└───────────────────────┘
```

- 番号を入れるたびに正規化して検索し、サークル名を表示する
- 見つからない場合は「カタログにありません」と出し、サークル名を手で入れて登録できるようにする（カタログ漏れ・誤記対策。手入力の印を付けて保存）
- 同じサークルに登録済みの購入物を先に見せ、重複登録を減らす
- 依頼人の初期値は「自分」。他の人の分も代わりに入れられる
- 既存の購入物に「自分も依頼する」ボタン。依頼人を1人追加するだけの操作にする

### 6.3 一覧画面

- 切り替え：**請負人ごと**（当日の買い出しメモ用）／**依頼人ごと**（自分が頼んだものの確認用）／**日・番号順**（会場の回り順の参考）
- 絞り込み：日、メンバー
- 請負人が未定の行は目立つ色にし、件数を上部に出す（会議の最後に残りを片付けるため）
- 各行をタップで編集

### 6.4 出力

| 出力 | 用途 |
|------|------|
| CSV（UTF-8 BOM 付き） | Excel や Google スプレッドシートで開く。列は R7 の 7 項目。依頼人は `;` 区切り |
| テキストのコピー | LINE・Discord などに請負人ごとの一覧を貼る |
| 印刷用表示 | 紙で持ち歩く場合 |

当日のみ公開なので、**会議の終わりに各自が出力して手元に残す**運用を前提にする。公開終了後はツールから取り出せない。

## 7. 同時編集の扱い

複数人が同時に操作するため、次のように決める。

- **依頼人の追加・削除**：配列への追加／削除の操作として送る（全体の上書きをしない）。同時に押しても両方残る
- **請負人・購入物・備考の変更**：`version` を比べて保存する。保存時に他の人が先に変えていたら「○○さんが更新しました」と出し、最新の内容を見せてから選び直してもらう
- **請負人の割り当て**：1人だけという制約はデータの形（単一値）で守る
- **削除**：取り消せるように、すぐには消さず「削除済み」の印を付ける。一覧からは隠す

## 8. 当日のみ公開する仕組み

二重に制限する。

1. **データの書き込み・読み出し**：サーバ側のルールで `open_from` ≦ 現在時刻 ≦ `open_until` の間だけ許す（Firestore ならセキュリティルールで書ける）
2. **ページの公開**：会議の前に公開し、終わったらホスティングを止める（または空のページに差し替える）

加えて、部屋の URL は推測されにくい文字列にし、Zoom のチャットで当日に配る。
会議後のデータは、出力を確認してから削除する。

## 9. 会議当日の流れ（想定）

1. 進行役が部屋を作り、メンバー名と時間帯を登録、URL を Zoom のチャットに貼る
2. 各自がスマホで開き、自分の名前を選ぶ
3. 各自が欲しい物を登録する（依頼人＝自分）
4. 進行役が「日・番号順」の一覧を画面共有し、1 件ずつ請負人を決める
5. 未定 0 件を確認する
6. 各自が出力（CSV またはテキスト）して保存する
7. 公開を止め、データを削除する

Zoom をスマホで使いながら同じスマホでツールを操作すると、アプリの切り替えが多くなる。Zoom は PC、ツールはスマホ、という使い方を勧める案内を出すか、要確認（Q5）。

## 付録：ダミーデータ

- `dummy-data/catalog.csv`：カタログ（何日目、サークル番号、サークル名）
- `dummy-data/assignments.csv`：分担の記録例（R7 の 7 項目）。依頼人が複数の例、請負人が未定の例、依頼人と請負人が同じ例、日が違う同じ番号の例を含む

サークル名・番号はすべて架空。
