# コミケ買い物分担ツール Blueprint（v0.4）

## 0. 変更履歴

| 版 | 内容 |
|----|------|
| v0.1 | 初版 |
| v0.2 | 決定事項を反映：最大 10 人、Firebase 採用、依頼人ごとの個数、金額は備考欄、Zoom は PC、公開 20〜24 時、企業ブースも扱う |

## 1. 目的

数人のチームが Zoom 会議をしながら、コミックマーケットで「誰が何を誰の代わりに買うか」を決めて記録する。
参加者は全員が自分のスマホで操作し、最後に一覧を表示・出力する。

## 2. 決定事項

| # | 項目 | 決定 |
|---|------|------|
| D1 | チームの人数 | 最大 10 人 |
| D2 | 共有データストア | Firebase（Firestore + Hosting） |
| D3 | 個数 | 依頼人ごとに個数を記録する |
| D4 | 金額 | 専用の項目は作らない。必要なら備考欄に書く |

| D6 | 公開時間帯 | 事前に固定しない。進行役が会議当日も含めていつでも設定・変更できる。入力欄の初期値は 20:00〜24:00（日本時間） |
| D8 | 進行役 | 1 人（このツールの依頼者本人） |
| D9 | Firebase のプラン | 無料プラン（Spark）。Cloud Functions は使わない |
| D7 | 企業ブース | 扱う |

## 4. 全体構成

```
[スマホのブラウザ] ──HTTPS──> [Firebase Hosting: HTML/JS/CSS + catalog.json]
        │
        └──リアルタイム同期──> [Firestore: 部屋・メンバー・購入物]
```

- **フロントエンド**：静的な 1 ページのアプリ。インストール不要。
- **カタログ**：読み取り専用。事前に `catalog.json` に変換して Hosting に置く。検索は端末内で行う。
- **共有データ**：Firestore に部屋ごとの購入物を置く。
- **認証**：Firebase Authentication の匿名ログイン。セキュリティルールで次のように分ける。
  - メンバー：ログイン済み かつ 部屋のメンバー かつ 公開時間内 だけ読み書きできる
  - 進行役：時間に関係なく、部屋の設定（時間帯・メンバー）の変更、一覧の閲覧・出力、データの削除ができる

人数は最大 10 人、件数も会議 1 回分なので、少人数の利用で無料枠に収まる見込み。
ただし料金・無料枠の数値は確認していないので、プロジェクト作成時に Firebase の最新の条件を確認する。

## 5. データモデル

### 5.1 カタログ（読み取り専用、`catalog.json`）

| 項目 | 型 | 例 | 備考 |
|------|----|----|------|
| `day` | 整数 | `1` | 何日目 |
| `kind` | `circle` / `corporate` | `circle` | サークルか企業ブースか |
| `circle_no` | 文字列 | `東A01a` / `企業101` | 正規化した形で持つ（5.3） |
| `circle_name` | 文字列 | `ダミーサークル壱` | 企業ブースでは出展者名 |

キーは `(day, kind, circle_no)`。日が違えば同じ番号でも別の出展とみなす（ダミーデータに例あり）。
企業ブースは複数日にわたって同じ番号で出ることがある想定だが、実際のカタログでどう表されるかは未確認。

### 5.2 Firestore の構成

```
rooms/{roomId}
  name, open_from, open_until, owner_uid
  members/{memberId}      name, uid（端末と紐づけた後に入る）, order
  items/{itemId}          購入物（下表）
```

#### 購入物 `items/{itemId}`

| 項目 | 型 | 必須 | 説明 |
|------|----|------|------|
| `day` | 整数 | ○ | 何日目 |
| `kind` | 文字列 | ○ | `circle` / `corporate` |
| `circle_no` | 文字列 | ○ | 正規化済みの番号 |
| `circle_name` | 文字列 | ○ | 検索時の値を写して保存する |
| `from_catalog` | 真偽値 | ○ | カタログに無く手入力した場合は false |
| `item` | 文字列 | ○ | 購入物 |
| `requests` | 対応表 `{memberId: 個数}` | ○（1 人以上） | 依頼人と個数（D3） |
| `assignee` | memberId / null | − | 請負人。1 人だけ。未定なら null |
| `note` | 文字列 | − | 備考。金額もここに書く（D4） |
| `created_by` / `updated_by` | memberId | ○ | |
| `updated_at` | 時刻 | ○ | |
| `version` | 整数 | ○ | 同時編集の検出用（8 章） |
| `deleted` | 真偽値 | ○ | 削除の印 |

依頼人を配列ではなく `{memberId: 個数}` の対応表にした理由：Firestore ではキーごとに個別に更新できるので、
A さんが自分の個数を変えている間に B さんが自分を追加しても、互いに上書きしない（8 章）。
キーに名前ではなく memberId を使うのは、名前の変更や記号を含む名前でも壊れないようにするため。

合計個数（請負人が買う数）は保存せず、表示と出力のときに `requests` から足して出す。

### 5.3 番号の正規化

スマホ入力の揺れをそろえてから検索する。

**サークル**
- 全角英数字 → 半角（`Ａ０１ａ` → `A01a`）
- 数字は 2 桁にそろえる（`東A1a` → `東A01a`）
- 末尾の `a` / `b` は小文字にそろえる
- 空白・`-` は取り除く

**企業ブース**
- 入力欄の横に「サークル／企業」の切り替えを置き、企業のときは番号を数字だけで入力できるようにする
- 正規化規則は、実際のカタログでの企業ブースの番号の書き方が分かってから決める。ダミーデータの `企業101` という形は仮のもの

サークル番号の実際の書式（ホール名の表記、ブロック文字の種類）も未確認。DB 入手後にこの規則を見直す。

## 6. カタログ DB の扱い

コミケ Web カタログからダウンロードできる DB の正確な形式（ファイル形式、列名、文字コード、企業ブースが含まれるか）は、こちらでは確認できていない。そのため次のように分ける。

1. **変換スクリプト**（事前に 1 回だけ実行）：入手した DB → `catalog.json`（5.1 の 4 項目だけ）
2. **アプリ**：`catalog.json` だけを読む

DB に企業ブースが含まれていない場合は、企業ブースの一覧を別に用意して変換時に足す。
または、企業ブースは常に手入力（`from_catalog: false`）で登録する。どちらにするかは DB 入手後に決める。

カタログデータを会議用ツールで使う際の利用条件も、DB 入手時に確認する（11 章 Q1）。
公開は部屋の URL を知る人に限り、当日の時間内だけにする。

## 7. 画面設計（スマホ縦画面）

画面は 4 つ。下部のタブで「入力」「一覧」「出力」を切り替える。

### 7.1 参加画面

- 部屋の URL を開くと表示される
- 「あなたは誰？」で自分の名前をタップする（最大 10 人なので 1 画面に収まる）
- 選んだ名前をその端末の匿名ログインと紐づける。次回からは自動で入る
- 進行役だけがメンバーを追加・変更できる

### 7.2 入力画面（中心の画面）

```
┌───────────────────────┐
│ [1日目] [2日目]          │
│ [サークル] [企業]         │
│ 番号 [東A01a          ]  │
│ → ダミーサークル壱        │ ← 一致したら即表示
│───────────────────────│
│ ここの登録済み            │
│  ・新刊セット 計3         │
│    依頼:A×1 B×2 請負:C   │
│    [自分も依頼] [編集]    │
│───────────────────────│
│ 購入物 [            ]   │
│ 依頼人と個数              │
│  A [−] 1 [+]  ✓          │
│  B [−] 0 [+]             │
│  …（最大10人）            │
│ 請負人 (1人)              │
│  (A)(B)(C)…(未定)        │
│ 備考 [              ]   │
│        [ 登録 ]          │
└───────────────────────┘
```

- 番号を入れるたびに正規化して検索し、名前を表示する
- 見つからない場合は「カタログにありません」と出し、名前を手で入れて登録できるようにする（`from_catalog: false`）
- 同じ出展先に登録済みの購入物を先に見せ、重複登録を減らす
- 依頼人の初期値は「自分 × 1」。他の人の分も入れられる
- 個数は `−` / `+` ボタンで変える。0 にするとその人は依頼人から外れる
- 既存の購入物の「自分も依頼」は、自分を 1 個で追加するだけの操作

### 7.3 一覧画面

- 並べ方の切り替え
  - **請負人ごと**：当日の買い出しメモ用。購入物ごとに合計個数と内訳（A×1, B×2）を出す
  - **依頼人ごと**：自分が頼んだものと個数の確認用
  - **日・番号順**：会議で 1 件ずつ決める用。サークルと企業ブースは分けて並べる
- 絞り込み：日、種別（サークル／企業）、メンバー
- 請負人が未定の行は目立つ色にし、件数を上部に出す
- 各行をタップで編集
- 進行役は PC のブラウザで同じ一覧を開き、Zoom で画面共有する（D5）。PC の横幅では表の形で表示する

### 7.4 出力

| 出力 | 用途 |
|------|------|
| CSV（UTF-8 BOM 付き） | Excel や Google スプレッドシートで開く |
| テキストのコピー | LINE・Discord などに請負人ごとの一覧を貼る |
| 印刷用表示 | 紙で持ち歩く場合 |

CSV の列：何日目、種別、サークル番号、サークル名、購入物、依頼人（`Aさん×1;Bさん×2`）、合計個数、請負人、備考

公開時間が終わるとメンバーはツールから取り出せないので、**会議の終わりに各自が出力して手元に残す**運用にする（進行役は時間外も出力できる）。
閉じる 30 分前になったら、画面上部に「○時○分で閉じます。出力を済ませてください」と出す。

## 8. 同時編集の扱い

最大 10 人が同時に操作する前提で、次のように決める。

- **依頼人の個数**：`requests.{memberId}` のキーだけを更新する。違う人の個数は同時に変えても互いに消えない。0 にしたらそのキーを消す
- **請負人・購入物・備考の変更**：トランザクションで `version` を比べて保存する。他の人が先に変えていたら「○○さんが更新しました」と出し、最新の内容を見せて選び直してもらう
- **請負人を 1 人に限る**：`assignee` を単一値にすることで、データの形で守る
- **削除**：`deleted: true` を付けて一覧から隠す。進行役は元に戻せる

## 9. 当日のみ公開する仕組み

二重に制限する。

1. **データ**：セキュリティルールで、メンバーには `open_from` ≦ `request.time` ≦ `open_until` の間だけ読み書きを許す。
   Firestore の時刻は UTC で比べるので、日本時間で入力した値を保存時に UTC に直す。
2. **ページ**：会議の前に Hosting に公開し、終わったら公開を止める（空のページに差し替える）。

### 9.1 公開時間帯の設定（D6）

時間帯は事前に固定せず、進行役が進行役画面でいつでも設定・変更できる。

- 入力欄の初期値は 20:00〜24:00（日本時間）。変えなければそのまま使う
- 当日に「今すぐ開く」「今すぐ閉じる」「30 分延長」のボタンを置く。会議が延びても、その場で延長できる
- 時間帯の変更は進行役だけができる。進行役自身は時間外でも操作できる（閉じた後の出力・削除のため）
- 変更はすぐ全員の画面に反映され、残り時間の表示も変わる。7.4 の閉じる前のお知らせは、閉じる 30 分前に出す
- 終了時刻が開始時刻より前になる、などの誤入力は保存前に止める

### 9.2 進行役の端末が変わったときの復旧（D9）

進行役の権限は、部屋を作った端末のブラウザの匿名ログイン（`owner_uid`）に紐づく。
そのブラウザのデータが消える、または別の端末を使う場合は、進行役の操作ができなくなる。無料プランのため自動の復旧は作らず、次の手作業で戻す。

1. 新しい端末でツールを開き、設定画面に出る「この端末の ID」をコピーする（全員の画面に表示する）
2. PC で Firebase コンソールを開き、Firestore の `rooms/{roomId}` の `owner_uid` をその ID に書き換える
3. ツールを再読み込みすると進行役画面が出る

予防として、進行役は部屋の作成と会議を同じ端末・同じブラウザで行い、プライベートブラウズは使わない。
手順は進行役向けの説明書に画面付きで書く（P5 までに用意）。

加えて、部屋の URL は推測されにくい文字列にし、当日に Zoom のチャットで配る。
会議後は出力が済んだことを確かめてから、Firestore の部屋データを消す。

## 10. 会議当日の流れ

1. 進行役が会議の前に部屋を作り、メンバー（最大 10 人）を登録する。時間帯は初期値のままでも、当日に決めてもよい
2. 開始時刻に公開（または「今すぐ開く」）。進行役が URL を Zoom のチャットに貼る
3. 各自が PC で Zoom に参加したまま、スマホで URL を開いて自分の名前を選ぶ
4. 各自が欲しい物と個数を登録する（依頼人＝自分）
5. 進行役が PC で「日・番号順」の一覧を画面共有し、1 件ずつ請負人を決める
6. 未定 0 件を確認する
7. 各自が出力（CSV またはテキスト）して保存する
8. 終了時刻に閉じる（延長する場合は「30 分延長」）。進行役が公開を止め、データを消す

## 付録：ダミーデータ

- `dummy-data/catalog.csv`：カタログ（何日目、種別、サークル番号、サークル名）。企業ブースを含む
- `dummy-data/assignments.csv`：分担の記録例。依頼人は `名前:個数` を `;` でつないだ形。
  依頼人が複数の例、個数が 2 の例、請負人が未定の例、依頼人と請負人が同じ例、日が違う同じ番号の例、企業ブースの例を含む。
  金額は備考欄に書いた例を 1 件入れた

サークル名・企業名・番号はすべて架空。企業ブースの番号の形は仮のもの。
